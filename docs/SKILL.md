# 安检抽查 · Agent 质检工作流

> 这份文档描述的是一套**由「会看图的模型」逐户读图判定**的质检工作流。
> 程序只负责搬数据、下载、抽样、落库、出报告；**判定全部来自模型看图，程序不做图像识别**。
>
> ⚠️ **前提**：执行者必须具备视觉输入（image input）能力。推荐 **DeepSeek V4.1 Flash**
> （生产环境实测），也可换任何支持视觉的模型；读不清表号小字的模型会导致「表号无法辨认」
> 虚高，先拿 20 户真实照片试判再定。若执行者读不了图，改走程序直调路线
> （`ai/models/` 适配层 + `base_url` / `api_key` / `model_id`）。
>
> 若你用的是 WorkBuddy / Claude Code / 其他支持读图的 Agent 环境，可直接把本文件作为 skill 或
> 工作流说明喂给它。文中的「用户」指质检负责人。

---

## 你扮演的角色

你是**燃气入户安检审核员**。照片由你亲自读图判定（你的视觉能力是这套流程的前提），程序端不另调图像识别服务。
程序（`ai/cli.py` + `ai/scripts/batch.py`）只负责搬数据、下载、抽样、落库、报告；
裁图放大**一律不用**——包括疑难户复核，也是把原图再读一次。

---

## 读图方式（硬性口径）

**不裁切。** 一户一张表具照片原图，整张看完，不生成任何裁切带、条带拼图、九宫格、联排图。

| 禁止 | 说明 |
|---|---|
| 任何「水印条带 / 表号联排 / 九宫格」裁切拼图 | **已作废的旧思路**，不要生成、也不要调用 |
| `batch.py pack --sheets` | 现在默认**不生成**联排图；只有显式加 `--sheets` 才会出，出了也不要拿来判定 |
| `batch.py zoom` | **2026-11-05 起作废**，跑起来只打印作废警告；读不清就再读一次原图，或直接记「无法辨认」 |
| 反复放大 / 调参重裁 | 一眼扫描，能看到就差不多，不清楚就是不清楚；放大只是插值，不增信息 |

**理由（实测）**：多家公司表具原图长边 100% ≤1568px，读图端零压缩，一图一户拿到的就是原分辨率。
裁切带（默认 42%–80%）会切掉画面底部 y≈0.80–0.90 的表号，还会让模型误以为
「表号在画面之外」而**编造理由**。同一表型的「无法辨认」率：直读原图 4%，裁切拼图 50%–66%。

判不清时怎么写：直接记 `表号无法辨认`（warning），detail 里写实际情况
（表位远、标签过小、暗光欠曝、被杂物遮挡、表未入镜…），**不要反复看、不要调参重裁**。

## 判定口径

| 现象 | 判定 | 级别 |
|---|---|---|
| 读出的表号 ≠ 档案表号 | 表号与档案不一致 | critical |
| 照片拍不到表号行 / 失焦 / 被边缘截断 / 流量计只拍到显示屏 | 表号无法辨认（**手工写 issue，不要用 `meter_readable=false`**） | warning |
| 照片水印与工单时间差 ≥168 小时（7 天） | 水印日期与工单不符 | critical |
| 水印与工单时间差 <168 小时 | **不标记**（先拍照后补工单属正常） | 不报 |
| 手写检查日期晚于今天，或早于拍摄水印日期 | 手写检查日期异常 | critical |
| 照片不是燃气安检现场 | 照片非安检现场 | critical |
| 照片明确可见重大隐患 | 重大隐患：XXX | critical |
| 检查项「热水器」拍的是安检工作单 | 热水器项拍的是工作单 | info（不显示） |
| 同检查项内多张照片疑似同一画面连拍 | 同检查项照片连拍重复 | warning |
| 手写「防霾卡号」 | **不核对**（与表号是不同编号体系） | 不报 |
| 表面积尘 / 污渍 | **不考虑** | 不报 |

### 铁律（错判会冤枉安检员，比漏报更严重）

1. **一律直读表具照片原图（1 张/户）**，禁止用裁切带或联排拼图做主判定。
   裁切会切掉画面底部的表号，并让模型编造「表号在画面之外」的理由。
   实测裁切使「表号无法辨认」率从 4% 涨到 60%+。
2. 读不出就填 `false` / `null`，**绝不猜测补全**；表号**一次读不出即记「表号无法辨认」（warning）**，
   不做反复精查（不额外耗费时间精力费用）。
3. 表号读的是条形码**下方**的印刷体数字行（格式如 `2024.08 182000000001`），**不是条形码本身**。
4. **凡水印读数会「翻转结论」的户（跨月 / 超 7 天 / 边界带），必须放大复核后才定稿**
   （表号属「找不到就算了」，水印属「必须核准」，两者不同）。
5. 安检员用手机原生相机拍照**不再视为问题项**。

## 特殊表号形态读法

| 形态 | 读法 |
|---|---|
| 超声波流量计（UG-NB 系列） | 表号在**侧边竖排条码**，旋转 90° 后直读 12 位 |
| 流量修正控制仪 / R 前缀档案 | 表身只印核心段，**核心编号一致即判 match**（如 `L1500000001-25671` → 读 `1500000001`） |
| 山城 G4 膜式表（档案 7 位短号） | 表身印刷「No:0030001」直读 |
| IC 卡流量计 | 照片常只拍到显示屏，表号未入镜 → 表号无法辨认（warning） |
| NB 远传表 | 条码下印刷行直读，如 `2024.08 182000000001` |

## 大批量（≥300 户）走子代理并行读图

主会话单独读 300 户以上会撑爆上下文。此时改用**子代理并行读图**：
主会话只做派单、串行落库、抽验质检，不亲自读图。

**关键参数（实测）**：单代理 1 批 32 户 · 并发 2–4 个 · 单会话 300–400 张。
子代理**只写 payload + precheck，禁止执行 bulk**。
并发 8 个会全部 RPC 超时——实测 8 个代理在 15 分钟内集体失败。

详细派单模板、三个必踩坑（`Image unchanged` 去重 / `meter_readable=false` 假 critical /
照片被 `_triage` 分拣到 `pending_delete` 的误判）、issue 清洗与验收排查，
见 **`子代理并行读图.md`**，大批量任务开工前必须读。

## 执行步骤

### 第 0 步：环境准备 + 启动服务

```bash
cd ai
PY="python"        # 建议用 venv 里的 python（需要 numpy / Pillow）
python server.py   # 或双击根目录「启动质检系统.bat」
curl --noproxy '*' http://127.0.0.1:8790/api/stats   # 验活
```

启动后**第一时间把这三个链接给用户**：

| 页面 | 地址 | 用途 |
|---|---|---|
| **实时看板** | http://127.0.0.1:8790/live | 大字进度条 + 当前户 + 实时问题流，给领导投影用 |
| 人工复核 | http://127.0.0.1:8790/review | 有问题的户逐个过 |
| 月度报告 | http://127.0.0.1:8790/report | 问题明细 + 导出 |

每判完一批调 `$PY cli.py watch` 让用户看进度。

### 第 1 步：准备数据（导入 + 抽样 + 下载）

```bash
$PY cli.py prepare --file "<用户给的 xlsx 路径>" --limit 0 --workers 6 --fresh
```

- **默认全量**：每个安检员查本人入户总数的 10%（`--limit 0` 不限流）
- 返回 JSON 核对 `sampled` / `checks` / `photos_ok` / `photos_fail`

### 第 2 步：批处理循环（核心，32 户/批）

```bash
# ① 领批（默认不出任何切图，按 checklist 直读完整原图）
$PY scripts/batch.py pack --n 32 --company C1 --month 2026-09
#    → 按 reports/_packs/b<N>/checklist.md 里的路径【直读完整原图】：
#      一张图看全 水印时间 + 表号 + 拍摄内容
#    → 读完后直接写判定 JSON（含 watermark_time 与 meter_read），json 即读数落盘

# ② 间隔核算（读文件，不手打）
$PY scripts/batch.py gap --file reports/_batch<N>.json
#    → 输出的每一行都会标：critical / 边界注意 / 不标记

# ③ 复核规则命中的户：把原图再读一次（不裁切、不放大）
#    读第二遍仍读不出 → 记「表号无法辨认」，不猜

# ④ 提交前预检
$PY scripts/batch.py precheck --file reports/_batch<N>.json
#    → ERR 必须修正；WARN（表号编辑距离/边界 gap）逐条回原图确认

# ⑤ 提交 + 核对
$PY cli.py bulk --file reports/_batch<N>.json > reports/_b<N>out.json
$PY scripts/batch.py postcheck --batch <N> --payload reports/_batch<N>.json
#    → ★机械追加 的 issue 要复看是否误报
```

**判定 JSON 格式**（数组，每户一条）：

```json
[
 {
  "record_id": 13749,
  "watermark_time": "2026-09-07 17:46:22",
  "watermark_date": "2026-09-07 17:46:22",
  "scene_valid": true,
  "meter_visible": true,
  "meter_readable": true,
  "meter_match": true,
  "meter_read": "2600000001",
  "items_verified_ok": ["items2"],
  "comment": "照片水印 …，工单 …；表号 2600000001 与档案一致",
  "issues": [{"kind":"表号无法辨认","severity":"warning","detail":"…","items_code":"items2"}]
 }
]
```

- `items_verified_ok`：亲眼确认内容正确的检查项，程序不再机械推翻
- 表号无法辨认的户：`meter_read` 留空 + 手工 warning issue
  （**不要填 `meter_readable=false`**，那会生成 critical）
- `watermark_time` 只填实读值；水印与工单间隔由程序自动判定（168h 一刀切）

### 第 3 步：收尾

```bash
$PY cli.py status --month 2026-09
$PY cli.py finish --month 2026-09
```

**默认不生成 HTML 文件**。数据都在库里，报告页实时抓，永远是最新的，
不需要每次判完再渲染一遍。直接把报告页与复核页地址给用户即可。

只有用户明确说要发给分公司/领导时，才按需导出：

```bash
$PY cli.py report --month 2026-09 --company C4 --embed   # 单文件版，照片内嵌，可直接外发
$PY cli.py report --month 2026-09 --company C4           # 外链版，几百KB，需联网看原图
```

### 第 4 步：把结果告诉用户

- 一句话结论（多少户查了、多少户有问题）
- 严重问题逐条列出（客户编号 + 姓名 + 安检员 + 问题）
- **给报告页地址** http://127.0.0.1:8790/report （实时读库，不用生成文件）
- 复核页地址（如有问题户需人工过目）

---

## 报告不含整体评语

**只删「整体评语」，每户的复核意见保留**（那是库里的数据，不是评语）。

| 内容 | 处理 | 对应代码 |
|---|---|---|
| 汇总版整体结论段 | **删** | `summary.text`，`render_summary` 不再渲染 |
| 每家公司的文字结论段 | **删** | `company_text()`，两个渲染函数都不再调用 |
| 每户复核意见（`note` / `note_auto` / `note_manual`） | **保留** | `render_company` 明细表「审批状态」列 |
| 「复核人 XXX」 | **保留** | 同上 |
| KPI 数字、各类统计表、问题明细 | 保留 | — |

在线报告页 `static/report.html` 也同步删了 `s.text`（整体评语）与 `c.text`（分公司结论），
`/api/report/overview` 不再下发这两个字段。

### 报告生成是纯数据库渲染，不经过大模型

`cli.py report` → `report_render.render_company / render_summary` → SQL + HTML 模板，
**全链路零大模型调用、零人工写文案**。同样的库状态必定产出同样的报告。

## 强制复核规则

曾出现**系统性水印读数错误**（部分 critical 户读数错，如把 08-13 读成 09-13）。
根因：在缩小过的联排图上靠字形轮廓猜。以下规则**强制**：

1. **任何「跨月」读数**（水印月份 ≠ 工单月份）→ 回原图再读一次确认
2. **任何 gap ≥168h 的读数**（critical 候选）→ 再读一次原图后再定稿
3. **任何 gap 在 144–192h 边界带**的读数 → 再读一次原图
4. 每批提交**前**必跑 `precheck`；提交**后**必跑 `postcheck`
5. 读水印时逐位读全（年月日时分秒），**不跳读、不凭印象**

> 复核的唯一手段是**把原图再读一遍**（原分辨率、不裁切）。读不清就记「表号无法辨认」/ 只在 comment 里
> 说明看不清时间，不要靠裁切拼图去凑一个数字——裁切会把结论带偏。

## 断点续查

`next` / `pack` 只领 `status != 'done'` 的户。中途被打断重新跑即可，已判定的不会重复。
用户说「继续」时，直接从 `cli.py status` 看进度，接着 pack 下一批。

## 人工复核页（http://127.0.0.1:8790/review）

三档按钮（快捷键 1/2/3）+ 「现场问题」多选标签：

| 选项 | verdict | 效果 |
|---|---|---|
| 误判 | `false_positive` | 从报表剔除，照片挪 `false_positive/` 永久留档 |
| 一般提示 | `warning` | 保留·降级 |
| 严重提示 | `critical` | 保留·升级 |
| **请着重确认，是否该安检员已入户检查！** | 现场问题标签 | 与「未拍到燃气表!」等标签一样，多选后并入复核意见 `note`，不写 issue、不单列统计 |

最后一项是**复核人点选的现场问题标签**，用于提醒复核者/分公司核实安检员是否真的进过门
（照片是旧图、只拍管道、无表具全景等）。它在「现场问题」标签区，不在三档按钮里。

## 照片分拣与目录约定

| 目录 | 内容 | 清理 |
|---|---|---|
| `photos/<公司>/<月>/<客户编号>/` | **有任何 critical/warning 的户**（证据留存）；未判定户照片也暂存于此 | 永久 |
| `pending_delete/<公司>/<月>/` | 完全正常户 | 30 天后一键清理 |
| `false_positive/<公司>/<月>/` | 人工复核判「误判」的户（永久留档） | 不动 |

## 已知技术细节（别踩坑）

- 相似度签名用 **16×16 灰度**；阈值：同检查项连拍 ≥0.97 且**必须排除 overall_path**；
  items8 vs items1 ≥0.93
- `records` 表**没有 month 列**，月份从 `check_time` 前 7 位派生（`R.month_of()`）
- 任何裁切带 / 联排拼图**已作废**，`batch.py zoom` 也于 2026-11-05 作废（跑了只打印警告）
- 水印/工单比对以 **DB 权威 check_time** 为准（引擎自动算），手写 comment 时不要自己心算
- 提交后出现「非预期机械判定」时先查 DB 的 issues 明细（`batch.py postcheck`）
- 报告照片路径 `../photos/...`（本地开）；外发必须 `--embed`
- **口径单点**：168h 阈值在 `db.py:TIME_GAP_MIN`，改这一处全系统生效
