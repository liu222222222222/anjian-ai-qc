# 子代理并行读图法（900+ 户大批量实战定案）

大批量（≥300 户）时，主会话单独读图会撑爆上下文。用多个子代理并行读图，
主会话只做「派单 + 落库 + 质检」，不亲自读图。

---

## 一、核心参数（实测得出，照抄即可）

| 项目 | 取值 | 依据 |
|---|---|---|
| 单代理批量 | **1 批 = 32 户** | 超过 32 户单代理耗时长、超时概率陡增 |
| 并发上限 | **2–4 个** | 8 个并发 → 全部 RPC 超时（`PacRpcClient request timed out after 5000ms`） |
| 单会话总量 | 约 300–400 张（≈10 批） | 再多则上下文与内存双双吃紧 |
| 子代理权限 | **只写 payload + precheck，禁止 bulk** | bulk 会 _triage 移动照片，多代理同时 bulk 会互相踩 |

**教训（实测）**：先按 8 个并发派单，8 个代理在 14–15 分钟后**全部超时失败**，
且失败代码是 `400 PacRpcClient request timed out` / `the request parameters were rejected by the model provider`。
降到每代理 1 批、并发 2–4 个后，稳定跑完。

## 二、派单模板（复制改批次号即可）

```
你是<公司>安检照片质检子代理。**开工前必须先完整 Read `docs/SKILL.md`（绝对路径）**，
严格按其流程与判定口径执行。只做 1 批 32 户，高效完成，不要做多余探索。

批次 <N> 的 rid（32个）：
<逗号分隔的 rid>

流程：
cd <项目根目录>/ai
PY="python"
PYTHONPATH=. $PY scripts/batch.py pack --batch <N> --rids <rids> --company <CO> --month 2026-09 --no-sheets

Read `reports/_packs/b<N>/checklist.md` → 逐张 Read 清单里的原图绝对路径
（一户一张，禁止裁切/拼图/zoom）→ 写 `reports/_batch<N>.json`
→ `PYTHONPATH=. $PY scripts/batch.py precheck --file reports/_batch<N>.json`

**绝对不要执行 `cli.py bulk`**。

回报：一行纯文本 `批次<N>：32户，表号一致 X，无法辨认 Y，critical <rid列表>；precheck ERR/WARN 结论`。
不要贴 JSON、不要发图。
```

**为什么要求「一行纯文本回报」**：子代理若把 32 条 JSON 全贴回来，主会话上下文会被瞬间吃掉，
后面几个代理的回报就挤不下了。只回摘要，明细在 payload 文件里。

## 三、主会话职责（落库 + 质检，别偷懒）

```bash
# 1) 收一个 payload 就立刻落库（串行，一次一批）
PYTHONPATH=. $PY cli.py bulk --file reports/_batch<N>.json

# 2) 查进度（pending 归零才算完）
PYTHONPATH=. $PY cli.py status --company C4 --month 2026-09

# 3) 全部判完后收尾
PYTHONPATH=. $PY cli.py retriage --company C4 --month 2026-09
PYTHONPATH=. $PY cli.py finish   --company C4 --month 2026-09
PYTHONPATH=. $PY cli.py report   --company C4 --month 2026-09
```

**代理失败了不要重跑已完成的部分**：先 `ls reports/_batch<N>.json` 看 payload 在不在。
子代理常在「写完文件、还没回报」的瞬间被超时打断——**payload 已落盘，大概率不用重跑**。
多次代理失败里，只有少数是真的没产出。

## 四、三个必踩的坑（都已在实战中遇到）

### 坑 1：Read 返回 `Image unchanged`，拿不到图

连续读**同一张图**时，Read 会去重并返回 `[Image reference] Same image content as previously loaded`，
等于没看到图。**这会让人误判成「看不清」**——比漏读更危险。

绕法：生成一张内容确实不同的副本再读。

```python
from PIL import Image
im = Image.open(src).convert('RGB')
w, h = im.size
im.resize((int(w*0.88), int(h*0.88)), Image.LANCZOS).save(dst, quality=95)
```

缩放系数取 0.88 或 0.97（只要不是 1.0），1px 差异即可绕过去重。
**注意**：简单 `cp` 到别的目录**无效**——去重是按内容哈希，不是按路径。

### 坑 2：代理写 `meter_readable=false` 会生成假 critical

`cli.py:335` 有机械兜底：`meter_readable=false` → 追加 **critical「表号读不出」**。
曾因此产生一批假 critical（问题户数一度虚高，修正后才回落）。

**正确写法**：表号读不出时**直接省略** `meter_readable` / `meter_match` / `meter_read` 三个字段，
只在 `issues` 里写一条 warning：

```json
{"kind":"表号无法辨认","severity":"warning","detail":"实际原因","items_code":"items2"}
```

### 坑 3：照片「被删了」——其实是 `_triage` 分拣

`cli.py bulk` 落库时会对每户跑 `_triage`：**无 critical/warning 的户，照片被移动到
`pending_delete/<公司>/<月>/<客户编号>/`**（30 天后清理，是既定设计）。

所以：
- 代理重跑已完成批次时，会看到 `File does not exist` 而惊慌 → 照片在 `pending_delete/` 里
- **代理 prompt 里要写明这一点**，并给出 fallback 路径
- 判别方法：`photos/` 目录变空 + `pending_delete/` 文件数同步增长 = 正常分拣；
  两边都少才是真问题

## 五、代理回报质量检查（主会话必做）

收到回报后，抽 3 类各 1 户回原图核对，别全信：

| 检查项 | 做法 |
|---|---|
| critical 户 | 回原图逐位对表号，确认不是抄错/看串行 |
| 「无法辨认」占比异常高 | 抽 2 户看是否其实是 `Image unchanged` 导致的假性看不清 |
| 「真换表」结论 | 位数相同但后段完全不同 → 真换表；去掉前导位后相等 → 同一表，不能判 critical |

抽验若干户的 critical 结论，全部成立，才确认整批可信。

## 六、issue 去重与清洗（收尾前必跑）

批量判定常见三类脏数据，落库后统一清洗（先备份 DB）：

```bash
cp db.sqlite3 backups/db_$(date +%Y%m%d)_before_cleanup.sqlite3
```

1. **`表号读不出` 与 `表号无法辨认` 是同一件事** → 合并为 `表号无法辨认`
2. **同户同 kind 重复**（payload 手写 + 程序机械追加各一条）→ 保留 detail 最长那条
3. **`照片非安检现场`（空 detail）与 `照片非燃气安检现场`（有 detail）重复** → 保留有 detail 的

清洗完必须重跑 `retriage` + `finish` + `report`，否则报告数字还是旧的。

## 七、验收脚本会报「报告数字 ≠ 首页数字」时的排查

一户**同时命中 critical 和 warning** 时：
- 报告侧按「一户一档、critical 优先」算 → 该户只计入 critical
- 首页侧若用 `COUNT(DISTINCT record_id)` 分档 → 两边都算，且
  `ok_house = recs_done - hcrit - hwarn` 会把这户**重复减掉**

修法（`server.py` 首页统计）：按户聚合后取 critical 优先，**用 `MIN` 不是 `MAX`**
（字符串序 `'critical' < 'warning'`，MIN 才是 critical）。

```sql
SELECT record_id, MIN(eff_severity) s FROM v_issue_eff
WHERE company=? AND eff_severity IS NOT NULL GROUP BY record_id
```
